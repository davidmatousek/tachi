# Feature Specification: Adoption Signal Capture (F-3, BLP-04 Wave 3)

**Feature Branch**: `305-adoption-signal-capture`
**Created**: 2026-06-01
**Status**: Draft
**Input**: PRD 305 — "Adoption Signal Capture (BLP-04 Wave 3)": build the *receiving infrastructure* (adopter case-study template, `docs/adopters/` index, reuse of the existing "In the Wild" Discussions category, a soft outreach round to warm prospects, AIVSS v1.0 release tracking, and a gitignored internal append-only signal log) so the inbound generated by F-1 (#296) and F-2 (#302) is captured and structured instead of evaporating.

## User Scenarios & Testing *(mandatory)*

This feature delivers **receiving infrastructure, not content**. Every story is independently testable, and the in-repo artifacts (template, index, CHANGELOG) form a viable MVP on their own — the platform-config and outreach stories layer activation on top.

### User Story 1 — Self-serve submission path (maintainer) (Priority: P1)

When an adopter reaches out wanting to share their experience, I want a structured case-study template so they have a clear, self-serve submission path instead of an ad-hoc email thread.

**Why this priority**: The template is the keystone artifact. Without it there is no submission path and every other story (index, channel, outreach) has nowhere to route. It is the smallest slice that delivers standalone value.

**Independent Test**: Open `docs/adopters/case-study-template.md` and confirm every field needed to convey production use is present, labeled required vs optional, and that a consent grant is captured at submission. Fully testable by inspection of one file.

**Acceptance Scenarios**:

1. **Given** the template file exists, **When** a prospective contributor opens it, **Then** it contains required fields for adopter org/identifier, scale of use, integration point, capabilities used, and outcomes — each clearly marked required.
2. **Given** the template file exists, **When** a contributor reviews the optional section, **Then** logo, pull-quote, and an external public-reference link (blog/slides/video) are present and clearly marked optional.
3. **Given** the template file exists, **When** a contributor reaches the consent section, **Then** an explicit permission block asks (a) may we publish your org name? (yes / anonymized / no), (b) may we use your logo? (yes / no), and (c) preferred attribution + contact — so consent is recorded *at submission*, not assumed afterward.
4. **Given** the template, **When** a single respondent completes it in one pass, **Then** no field requires a follow-up round-trip to convey production use (single all-in-one template; NFR-3 completeness).

### User Story 2 — Peer-signal channel (adopter) (Priority: P1)

When I use tachi in production and want to tell others, I want a dedicated public Discussions channel so other prospective adopters can find peer signal without contacting me privately.

**Why this priority**: Social proof must be publicly visible for procurement to trust it. Reusing the existing "In the Wild" category makes this a low-cost, high-leverage activation.

**Independent Test**: Visit the repository Discussions as a logged-in user and confirm the "In the Wild" category is publicly visible with a welcome post that explains how to post an adopter story or link a case study. Testable independently of the in-repo docs.

**Acceptance Scenarios**:

1. **Given** the repository Discussions, **When** a logged-in GitHub user browses categories, **Then** the existing "In the Wild" category is publicly visible and used as the adopter-stories channel (no redundant new category is created). `[MANUAL-ONLY] GitHub platform state is not represented in the repository`
2. **Given** the "In the Wild" channel, **When** a visitor opens the welcome post, **Then** it explains how to post an adopter story and links to both the case-study template and the adopters index. `[MANUAL-ONLY] Discussion post content is platform state`
3. **Given** the welcome post is pinned, **When** the maintainer records the pin, **Then** the pin method and slot accounting are documented and the global 4-pin ceiling is not exceeded. `[MANUAL-ONLY] pin placement is platform configuration`

### User Story 3 — Inbound ledger (maintainer) (Priority: P1)

When an inbound signal arrives (inquiry, citation, procurement-checklist appearance, traffic spike, adopter story), I want to log it in one place in a consistent shape so initiative-level adoption tracking becomes decidable rather than aspirational.

**Why this priority**: This is the "capture" half of the feature's value. A uniform ledger is what makes "is adoption happening, and should the next hardening initiative be prioritized?" a mechanical question rather than a guess.

**Independent Test**: Add one entry to the signal-log section in the gitignored `_internal/` workspace and confirm it follows the canonical shape and that `git status` shows no `_internal/` path. Testable independently of any public artifact.

**Acceptance Scenarios**:

1. **Given** the internal signal-log section exists, **When** a signal is logged, **Then** the entry follows the canonical shape **date · source · signal-type · decision**, where signal-type is drawn from a closed vocabulary (e.g., `inquiry | citation | procurement-mention | traffic | adopter-story`).
2. **Given** the signal log lives in the gitignored `_internal/` workspace, **When** the feature branch is staged, **Then** `git status` shows no `_internal/` path and no signal-log content appears in any tracked file.
3. **Given** the existing re-evaluation-log table in the same `_internal/` file, **When** the signal-log section is added, **Then** it is a distinct append-only subsection (its own column schema) and does not overload the existing 2-condition gate-decision table. `[MANUAL-ONLY] target file is gitignored and inspected locally`

### User Story 4 — Procurement validation (prospect) (Priority: P2)

When I evaluate tachi for procurement, I want to find the submission path and any captured adopter stories in one place, so the tool carries external validation, not just self-description.

**Why this priority**: Depends on US-1 (template) and US-2 (channel) existing; it is the discoverability layer that ties them together. Valuable but not the keystone.

**Independent Test**: Land on `docs/adopters/README.md` and confirm the "How to submit" pointer routes to the template and the channel, and that the index renders correctly on GitHub with an acceptable empty state.

**Acceptance Scenarios**:

1. **Given** `docs/adopters/README.md` exists, **When** a prospect opens it, **Then** a "How to submit" pointer routes to both the case-study template and the "In the Wild" channel.
2. **Given** no case studies have been captured yet, **When** a prospect views the index, **Then** an explicit, non-broken empty state is shown (the index is valid before any adopter surfaces).
3. **Given** the index file, **When** rendered on GitHub, **Then** all internal links (template, channel) resolve and the document renders without broken markdown.

### User Story 5 — AIVSS release watch (OWASP-ecosystem participant) (Priority: P3)

When OWASP releases AIVSS v1.0, I want the release tracked so tachi's response stays timely (Feature 143 already evaluated AIVSS; F-3 keeps the watch warm — it does not re-evaluate).

**Why this priority**: Smallest, most independent slice — a single tracking comment plus a pin. Valuable for timeliness but isolable from the adopter-docs core.

**Independent Test**: Open Issue #168 and confirm it carries a partial-scope tracking comment (watch covered here; technical evaluation is a separate future initiative) and is pinned.

**Acceptance Scenarios**:

1. **Given** Issue #168 is open, **When** F-3 closes, **Then** #168 carries a comment scoping F-3 to the AIVSS *watch* only and naming the evaluation as a separate future initiative. `[MANUAL-ONLY] GitHub Issue comment is platform state`
2. **Given** Issue #168, **When** the maintainer pins it, **Then** the watch is visible via an issue pin (issue-pin pool has headroom; does not touch the global discussion-pin pool). `[MANUAL-ONLY] issue pinning is platform configuration`

### Edge Cases

- **No inbound after distribution (R1)**: If F-1/F-2 generate no responses, the template/channel/log sit empty. An empty ledger is a valid, decidable result — the index shows an explicit empty state and BLP-03 simply stays deferred. Empty state is not a failure.
- **Submission without consent**: If a submission omits or denies name/logo consent, nothing identifying is published — default is private; publication requires an explicit grant captured in the template's consent block.
- **Signal-type outside the closed vocabulary**: A new inbound type that does not fit the enum is recorded only after the controlled vocabulary is deliberately extended — preventing interpretive drift in the ledger.
- **Global pin ceiling pressure**: The global pinned-discussion pool is at 3/4. Pinning a welcome post must not silently consume the last global slot when a zero-global-cost surface (category-level pin or category description) is available.
- **Outreach reads as spam (R2)**: A message that lands as a cold pitch damages reputation. Sends are restricted to previously-engaged contacts and pass a pre-send tone review before going out.
- **Commercial-framing leak (R5)**: Buyer-signal/pricing language must not migrate from the internal log into any public artifact. Public docs use neutral, adopter-facing language only.

### Key Entities *(include if feature involves data)*

- **Adopter case study**: a structured submission describing one adopter's production use. Required attributes: org/identifier, scale of use, integration point, capabilities used, outcomes. Optional: logo, pull-quote, public-reference link. Carries a consent grant (name / logo / attribution). Lives in `docs/adopters/` only after explicit consent.
- **Signal-log entry**: an append-only record of one inbound adoption signal. Fields: date, source, signal-type (closed vocabulary), decision. Lives only in the gitignored `_internal/strategy/BLP-03-signed-updates.md`.
- **Outreach recipient**: a previously-engaged prospect contacted in the soft outreach round. Identity stays private to Issue #305; never published without consent.
- **AIVSS watch record**: the partial-scope tracking comment + pin on Issue #168 marking the release watch (not the evaluation).

## Assumptions

- **A1 — Template shape (resolves Q2)**: a single all-in-one template (required core + optional rich fields) is used, not split "quick intro" / "full case study" templates, to minimize submission friction (NFR-5).
- **A2 — Signal-log placement (resolves Q3)**: the signal log is a new append-only subsection in the canonical `_internal/strategy/BLP-03-signed-updates.md`, with its own `date · source · signal-type · decision` columns — distinct from the existing 2-condition re-evaluation-log table.
- **A3 — Channel (resolves Q1, confirmed at define)**: the existing "In the Wild" category is reused; its live description already names "Adoption stories," so no new category is created.
- **A4 — Release framing (resolves Q6, confirmed at define)**: `feat(305):` is used because the submission path + channel are user-visible capability; `/aod.deliver` runs post-merge release-please verification (memory `feedback_aod_deliver_release_gate.md`) with the F-212 marker-commit fallback if a release does not open.
- **A5 — Pin mechanics (Q5, mechanic deferred to plan)**: because the global pinned-discussion pool is at 3/4 and the global and per-category pin pools are independent, the welcome-pin SHOULD prefer a category-level pin (In the Wild's own 0/4 pool) or a category-description surface over the last global slot. The exact mechanic is a plan-stage decision.
- **A6 — Outreach is human-judgment work**: the ~2–3 day envelope holds because warm-prospect selection and tone review are think-time, not file volume; the privacy/consent pass is a review gate on every public artifact.
- **A7 — Case-study content is exogenous**: actual case-study text is co-authored later when an adopter surfaces; this feature builds only the receiving infrastructure.
